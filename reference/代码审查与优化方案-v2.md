## 2. 高优先级问题

### H1: `statistics.py` 单文件过大

- **文件**: `trace_pipeline/geology/statistics.py`
- **行数**: 1075 行
- **问题**: 集凸包计算、圆窗策略（4种）、评分系统、迹线分型、格式化输出于一体，Single Responsibility Principle 违反
- **建议**: 按职责拆分为 4 个文件：

```text
geology/
├── statistics.py          # 统计入口 + compute_trace_statistics
├── circle_window.py       # 圆窗策略：tangent/hybrid/concentric/auto + 评分
├── convex_hull.py         # 凸包面积计算
└── format.py              # format_statistics_box_lines 等格式化
```

### H2: `TraceData` 可变性问题

- **文件**: `trace_pipeline/models.py:39`
- **问题**: `TraceData` 是可变 dataclass（无 `frozen=True`），而 `RunConfig` 和 `RunResult` 均设为 frozen，风格不一致
- **风险**: `TraceData` 实例可能在流水线中被意外修改（尤其是 `endpoints`, `joint_strikes` 等 numpy 数组可变引用）
- **建议**:

```python
@dataclass(frozen=True)
class TraceData:
    scanline_azimuth: float
    count: int
    _endpoints: np.ndarray  # 私有化
    # ...

    @property
    def endpoints(self) -> np.ndarray:
        return self._endpoints.copy()  # 返回副本防变异
```

或保留 frozen，用 `object.__setattr__` 在 `__post_init__` 中设置数组（类似 `RunConfig` 的做法）。

### H3: `df.attrs` 脆弱模式

- **文件**: `trace_pipeline/io/excel_writer.py:59-65`
- **问题**: 使用 `pd.DataFrame.attrs` 存储 section title，pandas 的 attrs 在切片/合并等操作后可能丢失
- **建议**: 定义独立数据结构代替：

```python
@dataclass
class ExcelSection:
    df: pd.DataFrame
    startrow: int
    startcol: int
    header: bool
    title: str
```

### H4: `dip_to_strike` NaN 安全缺陷

- **文件**: `trace_pipeline/geology/angles.py:43`
- **问题**: 第 43 行使用 `np.empty_like(dd, dtype=float)` 初始化结果数组。三个 mask（`mask_lt90`、`mask_mid`、`mask_ge270`）分别覆盖 `dd < 90`、`90 <= dd < 270`、`dd >= 270`，三者互斥完备。但 NaN 值使所有比较运算返回 False——`NaN < 90.0` 为 False、`NaN >= 90.0` 也为 False——导致 NaN 位置不匹配任何 mask，结果数组中对应位置保留 `np.empty_like` 的未初始化随机值
- **风险**: NaN 输入产生看似合理但实为垃圾的数值输出，下游计算不会报错但结果错误
- **建议**:

```python
# 方案 A：初始化为 NaN，使未覆盖位置自然传播
res = np.full_like(dd, np.nan, dtype=float)

# 方案 B：入口处拒绝 NaN
if not np.all(np.isfinite(dd)):
    raise ValueError("dip_deg 包含 NaN 或 inf")
```

### H5: `_shift_to_nonnegative` 引用 vs 副本不一致

- **文件**: `trace_pipeline/geology/transforms.py:47-48`
- **问题**: 当 `dx == 0.0 and dy == 0.0` 时直接 `return arr`（返回原数组引用），否则 `return arr + np.array(...)` 返回新数组。函数的行为取决于数据值：相同调用方式，有时修改返回值会影响原数组，有时不会
- **风险**: 调用方对返回值的修改可能意外污染原始数组；且此行为与模块设计意图（"不修改入参"）矛盾
- **建议**: 将第 48 行 `return arr` 改为 `return arr.copy()`

```python
if dx == 0.0 and dy == 0.0:
    return arr.copy()  # 保持一致：始终返回新数组
```

### H6: 端点计算就地修改违反"纯函数"声明

- **文件**: `trace_pipeline/geology/endpoints.py:196-252`
- **问题**: `_compute_left_only`、`_compute_right_only`、`_compute_bilateral` 三个函数通过 `X1[mask] = ...` 就地修改传入的数组参数，返回 `None`。模块 docstring 第 1 行声明 `"""端点坐标的向量化计算（纯函数，无 IO）。"""`，与实际行为矛盾
- **风险**: 当前调用方 `compute_endpoints`（第 311 行）中 X1/Y1/X2/Y2 是本地创建的零数组，实际无害。但若按 docstring "纯函数"理解来复用这些内部函数，则会意外修改调用方数据
- **建议**: 两种修复路径：
  1. 修正 docstring 为 `"""端点坐标的向量化计算（内部函数通过就地修改实现高效计算）。"""`
  2. 重构为返回新数组，使实现真正符合纯函数语义

### H7: 玫瑰图径向范围截断

- **文件**: `trace_pipeline/plotting/rose_plot.py:90`
- **问题**: `rmax = max(1, int(radii.max()))` 使用 `int()` 截断（向零取整），当 `radii.max()` 为 2.7 时 `rmax=2`，柱体超出 `ylim` 上限
- **风险**: 玫瑰图中频率最高的柱体被截断，视觉误导
- **建议**: 改为向上取整：

```python
import math
rmax = max(1, math.ceil(radii.max()))
```

### H8: 并行模式结果静默丢弃

- **文件**: `trace_pipeline/cli/dispatcher.py:77-102`
- **问题**: 并行分支初始化 `results: List[Optional[RunResult]] = [None] * total`（第 77 行），最终通过 `[r for r in results if r is not None]` 过滤（第 102 行）。虽然当前 `as_completed` 循环在正常情况下会填充所有槽位，但代码逻辑上存在窗口——若某个 future 因未被遍历到而保持 None，则对应结果被静默丢弃
- **风险**: 返回值 `len(results)` 可能小于 `total`，后续汇总报告缺少条目且无任何警告
- **建议**: 过滤后添加完整性检查：

```python
valid = [r for r in results if r is not None]
if len(valid) < total:
    logger.warning("并行执行结果不完整: 预期 %d，实际 %d", total, len(valid))
return valid
```

### H9: `dispatcher.py` 变量重绑定

- **文件**: `trace_pipeline/cli/dispatcher.py:77` 和 `:104`
- **问题**: `results` 变量在并行分支声明为 `List[Optional[RunResult]]`（`[None] * total`），在串行分支被重声明为 `List[RunResult]`，类型不一致
- **建议**: 拆分变量名或统一类型：

```python
# 并行
results_parallel: List[Optional[RunResult]] = [None] * total

# 串行
results_serial: List[RunResult] = []
```

### H10: Magic Number 不透明

- **文件**: `trace_pipeline/geology/statistics.py:905` 及 `:828-833`
- **问题**: `_AUTO_TIE_TOLERANCE = 0.12` 和评分因子（`1.45`, `1.00`, `1.35`, `1.10`, `1.00`, `1.10`）无注释说明数学推导
- **建议**: 提取为命名常量并添加注释：

```python
# 圆窗策略评分因子（经验权重，基于各指标对最终迹长估计精度的影响系数）
_SCORE_WEIGHTS = {
    "valid_group_count": 1.45,
    "valid_group_ratio": 1.00,
    "spatial_coverage": 1.35,
    "stability": 1.10,
    "radius_scale": 1.00,
    "sample_sufficiency": 1.10,
}
_AUTO_TIE_TOLERANCE = 0.12  # 评分分差 ≤12% 时回退到密度偏好策略
```

## 3. 中优先级问题

### M1: 使用旧式 typing 泛型

- **范围**: 全项目多处使用 `from typing import List, Dict, Tuple`
- **原因**: 项目 `requires-python = ">=3.9"`，Python 3.9+ 原生支持 `list[str]`、`dict[str, Any]`
- **建议**: 全局替换为内置泛型，仅保留需要 `typing` 的特殊类型（如 `Sequence`, `Mapping`）

### M2: `configure_style()` 每次扫描全系统字体

- **文件**: `trace_pipeline/plotting/style.py:53-54`
- **问题**: 每次调用 `configure_style()` 都会 `fm.fontManager.ttflist` 扫描全系统字体
- **建议**: 模块级缓存检测结果：

```python
_CJK_FONTS_CACHE: list[str] | None = None

def configure_style() -> None:
    global _CJK_FONTS_CACHE
    if _CJK_FONTS_CACHE is None:
        _CJK_FONTS_CACHE = _detect_cjk_fonts(CJK_SERIF_CANDIDATES) or _detect_cjk_fonts(CJK_SANS_CANDIDATES)
    # ... 后续逻辑
```

### M3: `excel_writer.py` 注释语言不一致

- **文件**: `trace_pipeline/io/excel_writer.py:1`
- **问题**: 模块首行 `"""Excel result writer with a summary-first single-sheet layout."""` 为英文，其余模块（excel_reader, discovery, pipeline 等）均用中文
- **建议**: 统一为中文：

```python
"""Excel 写入 — 四区布局单工作表输出。"""
```

### M4: 比例尺长度硬编码

- **文件**: `trace_pipeline/plotting/trace_plot.py:24`
- **问题**: `_FIXED_SCALE_LENGTH = 5.0` 比例尺固定为 5 米
- **建议**: 根据数据范围自适应或设为可配置参数

### M5: 异常捕获粒度过粗

- **文件**: `trace_pipeline/pipeline.py:146-151`
- **问题**: 非预期异常被 `except Exception as exc` 统一归类为"未预期错误"，丢失区分度
- **建议**: 增加分支：

```python
except (FileNotFoundError, ValueError, OSError, RuntimeError) as exc:
    logger.error("处理 [%s] 失败 (%s): %s", ...)
    return RunResult.failure(cfg.table_stem, str(exc))
except Exception as exc:
    logger.error("处理 [%s] 时发生未预期错误: %s", ..., exc_info=True)
    return RunResult.failure(cfg.table_stem, str(exc))
```

### M6: 缺少集成测试

- **文件**: `tests/` 下 18 个测试文件全为单元测试
- **问题**: 无端到端测试验证完整流水线（读取→计算→写入→绘图）
- **建议**: 新增 `tests/test_integration.py`，使用合成 Excel 输入文件在临时目录跑完整 `run_pipeline`

### M7: 缺少 `__version__`

- **文件**: `trace_pipeline/__init__.py`
- **问题**: 无版本属性，`pyproject.toml` 中 `version = "0.1.0"` 无法在代码中访问
- **建议**:

```python
# __init__.py
__version__ = "0.1.0"
```

并从 `pyproject.toml` 同步维护。

### M8: 缺少 `py.typed`

- **问题**: 无 PEP 561 类型标记文件，下游包的 mypy 无法读取 `trace_pipeline` 的类型信息
- **建议**: 在包根目录创建空文件 `trace_pipeline/py.typed`

### M9: `compute_endpoints` 返回 8 值 tuple

- **文件**: `trace_pipeline/geology/endpoints.py:260-263`
- **问题**: 返回 `Tuple[float, int, np.ndarray, np.ndarray, np.ndarray, np.ndarray, float | None, float | None]`，调用方需按位置解包，可读性差
- **建议**: 定义 `@dataclass EndpointResult` 承载返回值

### M10: 并行使用 `ThreadPoolExecutor` 而非 `ProcessPoolExecutor`

- **文件**: `trace_pipeline/cli/dispatcher.py:80`
- **问题**: `ThreadPoolExecutor` 受 GIL 限制，CPU 密集的统计计算无法并行
- **建议**: 使用 `ProcessPoolExecutor`（需注意 matplotlib 非线程安全，但流水线中每个进程各自创建图表，实际安全）

### M11: `fold_to_halfplane` 边界条件不一致

- **文件**: `trace_pipeline/geology/angles.py:119-123`
- **问题**: 当 `base <= 180.0` 时判定条件为 `(base < targets) & (targets < base + 180.0)`（开区间），当 `base > 180.0` 时为 `(base - 180.0 < targets) & (targets < base)`（同为开区间）。但两个分支的分界点 `base == 180.0` 走第一个分支，此时半平面为 `(180, 360)` 不含边界；而 `base == 180.0 + epsilon` 走第二个分支，半平面为 `(epsilon, 180+epsilon)`。边界值处行为跳变
- **风险**: 当目标角恰好等于 `base` 或 `base + 180` 时处理结果因浮点精度不同而不确定
- **建议**: 明确文档化边界行为，或统一为半开区间 `[base, base+180)`

### M12: `trace_plot.py` 装饰布局 20+ 魔法数字

- **文件**: `trace_pipeline/plotting/trace_plot.py:88-130` 等
- **问题**: 布局计算中散布大量未命名的比例系数：`0.68`、`0.54`、`2.00`（第 93 行）、`0.14`、`0.08`（第 103-106 行）、`0.76`（第 124 行）、`0.42`（第 128 行）、`0.014`、`0.022`（第 130 行）、`0.38`、`0.13`（第 219-220 行）、`0.91`、`0.82`、`0.98`（第 239-241 行）等 20+ 个，难以理解含义和调优
- **建议**: 提取为模块级命名常量或 `_LayoutConstants` dataclass，并注释每个值的含义

```python
# 面板模式下的右侧留白比例（相对于 x_span）
_PANEL_RIGHT_PAD_RATIO = 0.68
# 面板模式下的右侧留白比例（相对于 base_span）
_PANEL_RIGHT_PAD_BASE_RATIO = 0.54
# ...
```

### M13: `interactive.py` 异常链丢失

- **文件**: `trace_pipeline/cli/interactive.py:29` 和 `:37`
- **问题**: 两处 `except ValueError:` 直接 `raise ValueError(...)` 而未使用 `from exc` 语法，丢失原始异常堆栈

```python
# 第 28-29 行
except ValueError:
    raise ValueError(f"无效区间: {token}")  # 丢失原始 exc

# 第 36-37 行
except ValueError:
    raise ValueError(f"无效索引: {token}")  # 丢失原始 exc
```

- **建议**: 改为 `raise ValueError(...) from exc`

```python
except ValueError as exc:
    raise ValueError(f"无效区间: {token}") from exc
```

### M14: `setup_logging` 返回子模块 logger

- **文件**: `trace_pipeline/cli/logging_setup.py:68`
- **问题**: 函数内部正确配置了 `logging.getLogger("trace_pipeline")` 包级 logger（第 36 行），但第 68 行返回 `logging.getLogger(__name__)`（即 `trace_pipeline.cli.logging_setup`）。调用方（如 `main.py`）使用返回值记录日志时，logger 名称不是预期的 `trace_pipeline`
- **建议**: 返回包级 logger：

```python
return pkg_logger  # 即 logging.getLogger("trace_pipeline")
```

### M15: `RunResult.status` 弱类型

- **文件**: `trace_pipeline/models.py:247`
- **问题**: `status: str` 注释写 `"success" | "error"` 但无强制约束，调用方（`dispatcher.py:118`、`reporting.py:59,63,88,89`）均使用字符串字面量比较，拼写错误不会被检查
- **建议**: 使用 `Literal` 或 `Enum`：

```python
from typing import Literal

status: Literal["success", "error"]
```

### M16: `config.py` + `models.py` 配置校验重复

- **文件**: `trace_pipeline/config.py:156-171` 和 `trace_pipeline/models.py:178-213`
- **问题**: `validate_config()` 和 `RunConfig.__post_init__()` 都调用 `coerce_bool`、`coerce_positive_int`、`coerce_rose_bin_width`、`coerce_window_strategy` 等完全相同的校验函数，违反 DRY 原则
- **建议**: 由 `RunConfig` 的工厂方法（如 `from_mapping()`）调用 `validate_config()` 一次完成所有校验，`__post_init__` 仅做类型断言，不重复转换

## 4. 低优先级与代码风格

### L1: 内部函数缺失类型注解

- **位置**: `statistics.py` 中 `_cross`, `_bbox_overlaps`, `_side_height`, `_max_abs_y` 等多处
- **建议**: 补全类型注解提升可维护性

### L2: 表格列宽硬编码

- **文件**: `trace_pipeline/reporting.py:19`
- **问题**: `_COL_WIDTHS = [10, 8, 10, 10, 10, 8, 6]` 对中文内容可能过窄
- **建议**: 基于标题和内容动态计算列宽

### L3: `DEFAULT_CONFIG` 用 `Dict[str, Any]`

- **文件**: `trace_pipeline/config.py:30`
- **建议**: 定义 `TypedDict` 提供类型安全：

```python
class ConfigDict(TypedDict, total=False):
    input_dir: str
    output_dir: str
    output_prefix: str
    # ...
```

### L4: `pipeline.py` 冗余 `mkdir`

- **文件**: `trace_pipeline/pipeline.py:96`
- **问题**: `output_dir.mkdir(parents=True, exist_ok=True)` 在 `resolve_io_paths` 已被调用
- **建议**: 移除冗余调用或改为断言：

```python
assert output_dir.exists(), f"输出目录 {output_dir} 不存在"
```

### L5: 全局 `__all__` 缺失

- **文件**: `trace_pipeline/io/__init__.py` 和 `trace_pipeline/geology/__init__.py` 已有 `__all__`，但部分子模块（如 `logging_setup.py`, `args.py`）未定义
- **建议**: 所有子模块统一加 `__all__`

### L6: `tight_layout` + `bbox_inches="tight"` 冲突

- **文件**: `trace_pipeline/plotting/_helpers.py:40-41`
- **问题**: 第 40 行 `fig.tight_layout(pad=0.6)` 先调整子图布局，随后第 41 行 `fig.savefig(..., bbox_inches="tight")` 再次裁剪到紧凑边界。两者功能重叠，`tight_layout` 计算的间距可能被 `bbox_inches="tight"` 覆盖
- **风险**: 极端情况下可能导致标题或标注被裁剪
- **建议**: 二选一。推荐仅保留 `bbox_inches="tight"` 配合 `pad_inches`，移除 `tight_layout` 调用

### L7: `PROJECT_ROOT` 打包场景脆弱

- **文件**: `trace_pipeline/config.py:23`

### L9: 字体列表顺序影响西文排版

- **文件**: `trace_pipeline/plotting/style.py:66-68`
- **问题**: 第 68 行 `serif_list = primary_cjk + available_western + ["serif"]` 将中文字体（如 SimSun）排在列表首位。matplotlib 按顺序查找字形，西文字符也会优先尝试 SimSun 的西文字形。SimSun 的拉丁字母与 Times New Roman 风格差异明显，影响排版美观

- **建议**: 调整为 `available_western + primary_cjk + ["serif"]`，让 matplotlib 先用 Times New Roman 渲染西文，再 fallback 到 SimSun 渲染中文。但需实测验证不同 matplotlib 版本和后端下的行为
